# PokeOps: zero-dependency TCG seller platform — full-tree review (v1)

PokeOps implements the whole seller loop (scan → identify → value → single/bulk → listing → sell → fulfill → track profit) as a zero-dependency TypeScript app on Node 22 built-ins: `node:http` router, `node:sqlite` (`DatabaseSync`), `node:crypto` auth, server-rendered HTML, hand-drawn SVG charts. The four external "AI" capabilities (recognition, pricing, marketplace publish, assistant) plus classification and listing generation live behind interfaces in `src/services/interfaces` with deterministic mocks in `src/services/mock`. Build is clean, and 119 `node:test` cases pass across 25 files — they run real repositories/services against migrated in-memory SQLite and assert exact computed values, so they would fail if the logic were reverted. Per-user isolation, parameterized SQL (including the dynamic inventory search), scrypt+constant-time auth, and consistent HTML escaping are all in place, and the README status matrix is honest.

Watch for: the pricing engine is imported as a concrete mock singleton at seven route/service call sites rather than through one injection point, so that seam is weaker than the recognizer/publisher/listing seams (likely). `orders.net_revenue` is written as a net-of-cost-basis figure but is dead — never read — so its column name is misleading (confirmed). State-changing endpoints have no CSRF token and rely solely on `SameSite=Lax` (confirmed). None are blocking for a demo deliverable.

**Verdict**: APPROVED

## High-level view

The layering is disciplined: views render strings, routes call services, services call repositories, repositories own the SQL. Every user-owned repository method takes `userId` as its first argument and every query is scoped by it; API handlers gate on a `requireUser`/`requireAuth` check before touching data. I could not find a path that returns another user's rows.

The interface-decoupling story is real but uneven. `scanService`, `listingGenerator`, and `listingService` inject their capability through an interface-typed default parameter or factory (`runScan(input, recognizer: Recognizer = mockRecognizer)`, `createListingService(publisher = mockMarketplacePublisher)`), so a real implementation drops in by changing one default. The `PricingEngine` and `ClassificationService` are instead imported as concrete `mockPricingEngine`/`mockClassificationService` singletons directly in seven places (both pricing routes, the inventory route, the pricing API, `dashboardService`, `attentionService`, `recommendationService`). Callers still depend only on the interface's method shape, but swapping the engine means editing every call site — there is no single provider. Given the spec weight on swap-in, this is the one architectural gap worth naming.

Money math is centralized and consistent where it counts. `profitService.computeOrderProfit` is the single net-profit definition (sale − fees − shipping − packaging − cost basis − expenses), `recordSale` apportions order overhead across items and is idempotent, and analytics reads realized `net_profit`/`sale_price` straight from the `sales` table so the dashboard, analytics, and CSV exports agree. The pricing engine enforces the fast ≤ balanced ≤ max mode ordering, and the classifier is a genuine weighted multi-factor score (with an explicit net≤0 → BULK guard), not a lone price cutoff — the tests prove both.

Security posture is solid for the stated scope: scrypt with per-user salt and `timingSafeEqual`, HttpOnly/SameSite=Lax session cookies, all interpolated user data escaped via `escapeHtml`, the marketplace mock holds no credentials and does no network I/O, and the inventory search WHERE-builder is fully parameterized with a sort-column allowlist. The gaps are the absence of CSRF tokens and no `Secure` flag on cookies (fine for localhost, worth noting for real deployment), and the in-memory session store (already documented as future work).

Input validation follows the section-40 "never lose data" rule: the `Validator` collects field-level errors and applies only validated fields, partial inventory updates drop unvalidated keys rather than nulling them, CSV import reports bad rows without aborting the batch, and a recognizer throw marks the scan `error` while preserving the scan and any results.

### Interface decoupling: two tiers of seam

The recognizer, marketplace publisher, and listing generator are cleanly injectable. `scanService.runScan(input, recognizer: Recognizer = mockRecognizer)` and `createListingService(publisher: MarketplacePublisher = mockMarketplacePublisher)` both take the capability as an interface-typed parameter defaulting to the mock, and the route layer never references a mock. `createListingGenerator(pricingEngine: PricingEngine = mockPricingEngine)` is a factory with the same property. For these three, the swap-in claim in the README is literally true: change the default (or pass a different implementation) and nothing else moves.

The pricing and classification seams are only decoupled at the type level. Seven modules `import { mockPricingEngine }` (and two also import `mockClassificationService`) and call them as singletons:

```
api/pricing.ts, routes/pricing.ts, routes/inventory.ts   -> mockPricingEngine + mockClassificationService
services/dashboardService.ts, attentionService.ts,
  recommendationService.ts, listingGenerator.ts          -> mockPricingEngine
```

Because every caller only uses `getMarketData` / `priceCard` / `classify` — the interface surface — a replacement is behavior-compatible. But there is no `pricingEngine` provider to reassign, so the swap is a seven-file edit rather than a one-line change. A small `services/providers.ts` exporting `export const pricingEngine: PricingEngine = mockPricingEngine` that callers import would close the gap and match how the other seams already work.

### Net-profit definition and the dead `net_revenue` column

`computeOrderProfit` is the one place net profit is defined, and everything downstream derives from the `sales` rows `recordSale` writes:

```
net = salePrice - fees - shipping - packaging - costBasis - otherExpenses
```

`recordSale` apportions order-level overhead (fees + shipping + packaging) across line items by unit-price share, so per-item sale rows sum back to the order breakdown, and it is idempotent (re-running returns the existing sale ids without double-recording). Analytics and CSV export both aggregate `net_profit`/`sale_price` from `sales`, so the reported numbers are internally consistent — verified against `profitService.test.ts`, which asserts the exact 76.45 and 34.05 nets and the idempotent re-record.

The wart is `orderService.createFromInventory`, which computes `net_revenue: salePrice - fees - shipping - packaging - acquisition_cost` and stores it on the `orders` row. That is a net *profit* figure living in a column named `net_revenue`, and a grep shows nothing ever reads the column back — profit for the order-detail view is recomputed live via `computeOrderProfit`. So this is not a double-count in any reported total; it is a misleadingly-named dead write that will trip up a future consumer who trusts the column name. Rename it, repurpose it as revenue-after-fees, or stop writing it.

### Classifier is genuinely multi-factor (evidence it isn't a threshold)

`mockClassificationService` builds a 0–100 score from four saturating factors (net after fees, raw value, demand proxy from sold-band width + inverse competition, competition) weighted by settings, gated by an explicit `estimatedNet <= 0 -> BULK` guard. The direct evidence this is not a lone price cutoff is in `mockClassificationService.test.ts`: a $5 card with punishing shipping falls to BULK while a healthy-net $5 card with the same headline value does not, and lowering `sellThreshold` measurably shifts more cards to SELL_INDIVIDUALLY. It also pins the spec's examples ($0.75 → BULK, $12/low-competition → SELL_INDIVIDUALLY, ~$3 → REVIEW-or-BULK) and the section-10 explanation format.

### Per-user isolation

Every user-owned repository method threads `userId` and every statement includes `WHERE user_id = ?` (or scopes through the owning parent, as `scanResultsRepository` does via `scans.user_id` in `scanService.getOwnedResult`). API handlers call `requireUser` (JSON 401) and page routes wrap in `requireAuth` (redirect to /login) before any query. Update/delete paths first `getById(userId, id)` and return 404 when the row isn't owned, so a guessed id from another account yields "not found" rather than a cross-tenant mutation. The assistant answers exclusively from `userId`-scoped services. I found no unscoped user-data query.

### SQL safety in the dynamic search

`inventoryRepository.buildWhere` is the only place SQL is assembled dynamically: it seeds the clause list with `i.user_id = ?`, pushes a `?` placeholder for every filter value, and resolves sort through a `SORT_COLUMNS` allowlist keyed by client token (unknown tokens fall back to `updated`) with direction constrained to `ASC`/`DESC`. No user string is concatenated into SQL. The one interpolation to watch is `analyticsService.bestBy(groupExpr)`, which builds `SELECT ${groupExpr}`; it is currently called only with hardcoded expressions (`s.name`, `c.rarity`, `COALESCE(c.pokemon_name, c.name)`), so it is safe today but would become an injection sink if a future caller ever passed request input — keep it internal.

### Data-loss safety on bad input and recognizer failure

The inventory update handler deletes any key that failed validation before writing, so a bad field in a PATCH never nulls existing data. CSV import validates each row independently, reporting `{row, message, raw}` for bad rows and continuing — a malformed row can't abort the batch. `scanService.runScan` persists the scan row first, runs recognition inside try/catch, and on a throw marks the scan `error` while returning the intact scan plus any results already written, rather than dropping the row. The multipart parser likewise never throws on a malformed body — it returns whatever it parsed so the base64 JSON fallback can take over. This matches section 40 end to end.
